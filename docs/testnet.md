# Menjalankan alur Sepolia

Prosedur untuk kontrak **v2** (protokol EIP-712 domain version `"2"`). Kontrak aktif, peran, dan transaksi deployment tercatat di [`docs/uas/DEPLOYMENT_RECORD.md`](uas/DEPLOYMENT_RECORD.md). Hasil uji end-to-end nyata di Sepolia (penerbitan, pencocokan FHE, pencabutan) tercatat di [`docs/uas/TEST_RESULTS.md`](uas/TEST_RESULTS.md). Tes FHEVM mock tetap bukan bukti dekripsi melalui layanan Zama sungguhan; kedua tingkat bukti dipisahkan di sana.

1. Siapkan PostgreSQL dan jalankan migrasi. Hosting memakai Supabase: `DATABASE_MIGRATION_URL` direct/session pooler port 5432 untuk `pnpm db:migrate`, `DATABASE_URL` transaction pooler port 6543 untuk runtime. Uji lokal memakai PostgreSQL lokal sekali pakai (mis. Docker) setelah migrasi; jangan menjalankan uji terhadap database hosting. Isi RPC Sepolia (`CHAIN_ID=11155111`), wallet deployer dengan test ETH, serta **lima alamat berbeda**: admin, attestor, relayer, result reader, dan signer institusi. Kunci layanan (attestor, relayer, reader) hanya di backend dan harus tiga kunci berbeda; backend menolak duplikat. Kunci admin dan signer tidak pernah dimasukkan ke konfigurasi backend; kampus memakai wallet browser dan tidak menyerahkan private key kepada form.
2. Relayer Zama Sepolia terbuka dan tidak membutuhkan API key; SDK browser maupun backend memakai `SepoliaConfig` tanpa `auth`. Lihat [dokumentasi autentikasi Zama](https://docs.zama.org/protocol/sdk/guides/authentication) dan [Relayer API keys](https://docs.zama.org/protocol/sdk/guides/relayer-api-keys). Kunci wallet relayer aplikasi tetap diperlukan untuk menandatangani transaksi pencocokan.
3. Preflight lalu deploy dari `contracts/` (tanpa `--execute` hanya menampilkan rencana; preflight memeriksa chain ID, empat alamat peran berbeda, signer yang direncanakan bukan akun layanan, dan saldo terhadap estimasi biaya):

```powershell
cd contracts
$env:ADMIN_ADDRESS="0x..."; $env:ATTESTOR_ADDRESS="0x..."; $env:RELAYER_ADDRESS="0x..."; $env:RESULT_READER_ADDRESS="0x..."; $env:PLANNED_SIGNER_ADDRESSES="0x..."
node --env-file=../.env node_modules/hardhat/internal/cli/cli.js uas:deploy --network sepolia --expected-chain-id 11155111
node --env-file=../.env node_modules/hardhat/internal/cli/cli.js uas:deploy --network sepolia --expected-chain-id 11155111 --confirmations 2 --execute
```

Tugas mencetak alamat, tx hash, dan blok dari receipt, lalu menulis record non-rahasia ke `contracts/deployments/sepolia/<alamat>.json`. Langkah lengkap (verifikasi source Sourcify, registrasi idempoten, pemeriksaan dan rotasi peran) ada di [`DEPLOYMENT_RECORD.md` bagian 4](uas/DEPLOYMENT_RECORD.md#4-reproduksi).

4. Simpan alamat sebagai `CREDENTIAL_CONTRACT_ADDRESS` dan blok sebagai `CONTRACT_DEPLOYMENT_BLOCK`, isi tiga private key layanan, gunakan `APP_MODE=testnet`, lalu mulai ulang aplikasi. Bila kontrak lama masih memiliki rekaman yang harus tetap terbaca, isi `LEGACY_CREDENTIAL_CONTRACTS=<alamat>:<blok batas>` (lihat bagian migrasi di bawah). OCR berjalan in-process di langkah Workflow; tidak ada worker atau service OCR terpisah. Pastikan `APP_ORIGIN` memakai origin kanonis tempat aplikasi diakses sebelum menerbitkan QR. `CHAIN_CONFIRMATIONS` minimal 2; pembacaan memakai blok `head - (confirmations - 1)` dan penerbitan yang baru ada pada tip ditandai `PENDING`.
5. Administrator membuka `/penerbit`, memilih **Hubungkan wallet** pada dialog RainbowKit, beralih ke Sepolia bila diminta, lalu menandatangani pesan masuk. Untuk koneksi HP/QR, isi `NEXT_PUBLIC_WALLETCONNECT_PROJECT_ID` dari Reown Dashboard sebelum build; lihat [konfigurasi login wallet](../README.md#login-wallet-kampus). Menghubungkan wallet saja belum membuat sesi login atau memberikan kewenangan. Daftarkan institusi dengan ID `bytes32` yang tetap, nama terverifikasi (maksimal 200 byte UTF-8), dan status aktif melalui `setIssuer(issuerId, name, active)`. Kemudian aktifkan wallet pejabat melalui `setSigner(issuerId, wallet, true)`. Keduanya transaksi yang berbeda. Portal menampilkan hash dan blok transaksi yang terkonfirmasi, atau error kontrak yang terdekode (mis. `SignerAlreadyActive` untuk aktivasi berulang, `RoleConflict` bila wallet memegang peran layanan/admin). Alternatif tanpa UI: `uas:register` (idempoten). ID institusi acak dapat dibuat secara lokal:

```powershell
node -e "console.log('0x' + require('node:crypto').randomBytes(32).toString('hex'))"
```

Simpan ID tersebut untuk administrasi dan rotasi berikutnya. Saat rotasi, nonaktifkan wallet lama dengan `setSigner(issuerId, oldWallet, false)` lalu aktifkan wallet baru untuk **ID institusi yang sama**. Riwayat kewenangan signer lama tetap tersimpan; menonaktifkan wallet lama tidak mencabut kredensial historis. Status kampus diubah melalui `setIssuer`, sedangkan pencabutan kredensial memakai `revoke(credentialId)` oleh signer kampus yang masih berwenang.

6. Kampus masuk dengan wallet terdaftar dan mengikuti **Isi data → Tinjau data publik → Sahkan kredensial → Kirim penerbitan → Unduh ijazah**. Gunakan data sintetis, misalnya nama `ANDI PRATAMA`, nomor `UAS/2026/A001`, program `INFORMATIKA`, tanggal `2026-08-15`. Profil publik memuat nama, nomor ijazah, program studi, dan nama kampus; tanggal lulus tetap privat. Atribut dienkripsi sekali sebelum peninjauan. Wallet mengesahkan pesan EIP-712 `CredentialAuthorization` (memuat `issuerNameHash`; ID kredensial diturunkan dari chain, kontrak, institusi, signer, dan nonce), kemudian menyetujui transaksi `issueCredential(authorization, signature, handles, inputProof)` secara terpisah. Mengubah data atau handle memerlukan persiapan dan pengesahan baru.

Payload dan signature disimpan sebagai bukti persisten sebelum transaksi dikirim. QR baru tersedia setelah konfirmasi yang disyaratkan dan pemeriksaan bukti terhadap kontrak berhasil. Jika pengiriman sudah menghasilkan tx hash lalu penantian konfirmasi gagal, gunakan pemeriksaan konfirmasi pada portal; jangan menerbitkan ulang hanya karena UI belum menerima receipt. Deadline pengajuan membatasi pengajuan baru, bukan masa berlaku kredensial yang sudah diterbitkan.
7. Gunakan PDF yang diunduh dari portal sebagai fixture: PDF itu memuat QR kredensial yang baru diterbitkan dan origin `APP_ORIGIN`. Variasi (atribut diubah, QR kredensial lain dengan atribut berbeda) dapat dibuat dengan `generateDiploma` dari `apps/web/src/server/diploma-pdf.ts`, seperti pada `apps/web/tests/e2e/sepolia.spec.ts`. Fixture dengan origin atau credential ID yang berbeda tidak mewakili penerbitan yang sedang diuji.
8. Pindai QR memakai kamera HP atau buka URL `/c/{credentialId}`. Halaman memverifikasi signature, hash snapshot publik, ikatan on-chain, kewenangan historis, serta status terkini. Hasil `VERIFIED_RECORD` bercakupan `RECORD_ONLY`, `documentDecision: null`, tanpa unggahan, login, wallet pemeriksa, OCR, atau transaksi baru. Jalur ini tidak memakai kunci relayer: QR tetap dapat diperiksa selama database bukti dan RPC tersedia. QR Andi pada dokumen Budi tetap menampilkan rekaman Andi; belum ada klaim bahwa isi kertas cocok.
9. Pilih **Periksa dokumen lebih lanjut**, unggah PDF, lalu pastikan keputusan berasal dari FHE. Catat tx hash penerbitan dan pencocokan secara terpisah, blok pembacaan status, hasil per field, serta laporan PDF bercakupan `CHECKED_ATTRIBUTES`. Jalankan perubahan field, QR kredensial lain, identitas tujuan tidak cocok, dan dokumen tanpa QR aplikasi. Rekaman `INVALID_PROOF`, `PENDING`, `ISSUER_INACTIVE`, atau `REVOKED` tidak menghasilkan transaksi pencocokan baru atau `MATCH`. Bila anggaran `MAX_COMPARISONS_PER_HOUR` habis atau saldo relayer kurang, pekerjaan berakhir tanpa transaksi dengan alasan yang jelas.
10. Cabut melalui portal; kedua jalur verifikasi ulang harus menunjukkan dicabut, halaman QR menampilkan jejak pencabutan (hash dan blok), dan unduhan PDF penerbit ditolak (HTTP 409). Uji pencabutan/deaktivasi selama pekerjaan berjalan, rotasi wallet setelah penerbitan, serta pembacaan setelah deadline pengajuan (tes terkontrol di `apps/web/tests` dan `contracts/test`). Setelah menghapus unggahan atau melewati TTL pekerjaan, profil publik dan bukti penerbitan harus tetap dapat dibaca.

Uji end-to-end otomatis melalui UI tersedia sebagai `apps/web/tests/e2e/sepolia.spec.ts` (opt-in, `SEPOLIA_E2E=1`; lihat [`docs/uas/DEMO.md`](uas/DEMO.md)). Spesifikasi itu memakai wallet uji khusus dan data sintetis serta mengirim transaksi nyata.

## Beralih ke kontrak baru (v1 → v2)

Kontrak ini bukan proxy yang dapat di-upgrade. Perubahan Solidity memerlukan deployment baru: bangun ulang ABI melalui `pnpm --filter @verifikasi/contracts build`, jalankan migrasi database, ubah alamat/blok deployment, lalu daftarkan institusi dan signer pada kontrak baru. Tanda tangan v1 tidak berlaku pada domain v2 (versi domain dan tipe `CredentialAuthorization` berbeda; diuji).

Rekaman pada kontrak lama tidak dihapus dan tidak dianggap palsu. Server membacanya **hanya-baca** melalui daftar kontrak tepercaya `LEGACY_CREDENTIAL_CONTRACTS=<alamat>:<blok batas>`; alamat kontrak tidak pernah diambil dari QR atau input pengguna. Rekaman v1 yang terbit setelah blok batas tidak dipercaya, dan pencocokan dokumen FHE tidak tersedia untuk rekaman v1 (hasil `INCONCLUSIVE` dengan alasan versi lama). Tanpa entri daftar tersebut, halaman QR menampilkan alasan versi lama yang akurat. Untuk menerbitkan ulang pada kontrak baru, lakukan penerbitan baru oleh pejabat (ID dan QR baru); tidak ada migrasi otomatis yang mengarang signature.

Pencocokan memiliki biaya test ETH dan akses layanan Zama. Gangguan RPC, kuota, saldo relayer, atau dekripsi ditampilkan sebagai menunggu/retry/ERROR, tidak diubah menjadi MATCH. RPC dibatasi 20 detik dan operasi proof/dekripsi 60 detik per panggilan. Pengujian lokal terhadap PostgreSQL lokal dan mock tidak membuktikan koneksi Supabase/Blob atau alur chain pada hosting. Situs Netlify belum diselaraskan dengan kontrak v2 dalam pekerjaan UAS ini; langkahnya ada di [`docs/uas/DEMO.md`](uas/DEMO.md).
