# Implementasi dan operasi

> Konteks versi, 4 Oktober 2026 (WIB): implementasi UAS memakai kontrak protokol v2 dan pembacaan v1 melalui daftar kontrak tepercaya dengan cutoff block. Netlify memakai Background Functions dan Netlify Blobs; Workflow SDK berlaku untuk lokal/Vercel. Uraian keputusan dan pengujian sebelumnya dipertahankan sebagai riwayat. Fakta arsitektur, ACL, peran, governance dan pengukuran lokal S-12 tersedia di [FAKTA_ARSITEKTUR_DAN_PENGUKURAN.md](uas/FAKTA_ARSITEKTUR_DAN_PENGUKURAN.md). Hasil final ada di [TEST_RESULTS.md](uas/TEST_RESULTS.md); penyelarasan produksi Netlify belum dilakukan, dan langkah pengguna ada di [DEMO.md](uas/DEMO.md).

Untuk deployment Netlify, penyimpanan memakai Netlify Blobs dan eksekusi pemeriksaan memakai native Background Functions, dengan lease pekerjaan di PostgreSQL dan pemulihan terjadwal. Konfigurasi dan langkah deploy ada di [panduan Netlify](netlify-storage.md). Penjelasan Workflow SDK berikut berlaku untuk Vercel dan pengembangan lokal.

Web/API Next.js memakai sesi HttpOnly, SameSite Strict, Secure pada origin HTTPS; setiap mutasi pengguna memeriksa origin dan CSRF. Di Vercel, browser meminta intent upload persisten, mengirim satu file langsung ke Blob privat dengan token berumur sepuluh menit, lalu memanggil API finalisasi. Server menentukan path, memeriksa kepemilikan, batas 10 MiB, ukuran/MIME aktual, signature PDF/JPG/PNG, SHA-256, kuota, dan idempotensi sebelum membuat pekerjaan. Digest browser hanya mengikat retry dan dihitung ulang dari byte sebenarnya. Multipart melalui API tetap tersedia untuk lokal. Tidak ada API publik untuk mengirim tebakan empat atribut. File dan hasil hanya tersedia bagi pemilik sesi.

Mode demo lokal dapat memakai JSON persisten dengan lock direktori dan penulisan atomik; Vercel dan mode testnet mewajibkan PostgreSQL. Drizzle ORM mengelola schema dan akses database; Drizzle Kit menerapkan migrasi yang dilacak dalam `apps/web/drizzle` sebelum aplikasi dijalankan. Runtime tidak melakukan DDL. Antrean prototipe disimpan dalam satu JSONB bertipe yang dikunci melalui transaksi `FOR UPDATE`. Model ini menyerialkan metadata dan belum diukur untuk beban produksi. Koneksi Supabase runtime memakai transaction pooler port 6543, tanpa prepared statement bernama; migrasi memakai koneksi direct/session port 5432. Tabel mengaktifkan RLS dan tidak memberikan akses browser.

Jalur Vercel memakai satu proyek Next.js dengan `apps/web/vercel.json`; OCR berjalan di dalam langkah Workflow, tanpa service, container, atau endpoint OCR terpisah. Workflow adalah jalur eksekusi Vercel dan lokal; jalur Netlify memakai Background Functions seperti dijelaskan di atas. Workflow menyimpan dispatch intent sebelum enqueue; run/generation token mencegah duplikasi mengambil alih pekerjaan yang sudah berjalan. OCR, pengiriman transaksi, pemeriksaan hasil, dan cleanup menjadi langkah terpisah. `sleep` menunggu di antara polling, sehingga request upload tidak menunggu blockchain. Retry memakai OCR dan transaksi privat yang sudah disimpan. Hanya ID dan metadata kendali yang melintasi boundary langkah Workflow; dokumen, URL privat, teks OCR, dan transaksi bertanda tangan tidak masuk history Workflow. [Panduan Vercel](vercel.md) memuat konfigurasi dan langkah migrasi dari konfigurasi Services lama.

Langkah OCR membaca `upload.bin` dari penyimpanan privat, memeriksa ulang ukuran dan SHA-256 terhadap digest yang difinalisasi, lalu memanggil `extractDocument` dari `@verifikasi/ocr`. Batasnya 210 detik per dokumen, 35 detik per halaman, maksimal lima halaman dan 20 juta piksel per halaman. Kesalahan dokumen (password, halaman berlebih, berkas rusak, resolusi berlebih) disimpan sebagai hasil; timeout dan kegagalan mesin OCR dilempar agar Workflow mengulang. Worker tesseract.js dibuat baru per dokumen dan dihentikan setelah selesai atau saat timeout. MuPDF dan zxing berjalan di sandbox memori WASM. Isolasi ini berbeda dari proses OS terpisah dengan RLIMIT pada worker Python sebelumnya; batas memori/CPU mengikuti Function Vercel dan perlu diukur pada cloud.

Paket runtime OCR (tesseract.js, MuPDF.js, zxing-wasm, data bahasa) tetap eksternal pada bundle Next.js dan dimasukkan utuh ke trace deployment. Path WASM zxing dan data bahasa di-resolve saat runtime dari direktori aplikasi; `scripts/check-deployment.mjs` membuktikan resolusi tersebut dari salinan trace terisolasi. Tidak ada unduhan jaringan saat OCR; logger tesseract.js dan peringatan MuPDF tidak dicetak ke log.

PDF dirender MuPDF.js pada 200 DPI; text layer tidak dibaca. Gambar dibuka sebagai image document MuPDF sehingga orientasi EXIF diterapkan. zxing-wasm membaca QR pada piksel asli; simbol yang terdeteksi tetapi gagal didekode dipertahankan sebagai kandidat kosong. Batas QR terdeteksi dimask putih (+10 px) sebelum Tesseract agar modul QR tidak terbaca sebagai kata. tesseract.js (`ind+eng`, PSM 6, data tessdata 4.0.0) mengeluarkan tabel TSV per kata; parser mengambil teks, kandidat, minimum confidence token per field, bounding box, halaman, dan versi konfigurasi `OCR_CONFIG.version` beserta hash-nya. Normalisasi akhir selalu dilakukan paket TypeScript domain. Angka 0,90 adalah ambang awal yang hanya diperiksa pada fixture; bukan probabilitas benar atau hasil kalibrasi luas.

Konfigurasi `tesseract-js-ind-eng-v5` menambahkan satu pembacaan ulang area atribut pada template PDF terbitan aplikasi (`D1`) jika confidence awal di bawah 0,90 dan kandidatnya tunggal. Area berasal dari bounding box OCR pada piksel halaman, ditambah padding 10 px. Teks pembacaan halaman dan area harus sama persis; perbedaan atau hasil kosong tetap tidak memenuhi syarat. Confidence memakai minimum token hasil pembacaan area, tanpa penambahan skor atau koreksi ke data referensi. Atribut yang sudah memenuhi ambang tidak dibaca ulang. Batas waktu dokumen juga berlaku untuk pembacaan tambahan ini. Ini deskripsi konfigurasi historis v5.

**Revisi 5 Oktober 2026:** konfigurasi `tesseract-js-ind-eng-v6` memakai ambang 0,70 dan memasukkan kebijakan confidence dalam hash. Domain hanya menolak karena confidence ketika keempat skor valid semuanya <0,70; satu skor ≥0,70 cukup untuk melewati gate confidence. Pembacaan ulang area D1 memakai ambang yang sama dan tidak memperbaiki skor invalid. Parser tidak menjepit skor atau menyembunyikan token invalid. Empat teks/kandidat/halaman/QR dan tanggal tetap wajib valid. Detail serta pemisahan confidence dari coverage dan keputusan FHE ada di [catatan kebijakan](uas/PERUBAHAN_KEBIJAKAN_OCR_70.md).

PDF penerbit dibuat langsung dari profil publik bertanda tangan yang rekamannya valid dan tanggal lulus privat dari penerbit, lalu diarsipkan tanpa OCR atau transaksi pencocokan FHE. Status `READY` berarti arsip tersedia, bukan keputusan `MATCH`. Verifikasi berkas unggahan tetap memakai OCR, ambang confidence, dan pencocokan FHE.

Dua template sintetis berlabel `VERIFIKASI TEMPLATE A1` (label Indonesia, tanggal DMY) dan `VERIFIKASI TEMPLATE B1` (label Inggris, tanggal MDY), serta template terbitan aplikasi `D1`, didukung parser. Empat field diberi label pada satu halaman. Dokumen kampus bebas di luar template ini dapat berakhir `INCONCLUSIVE`. Jangan menggunakan fixture sebagai ijazah resmi.

## Blockchain

`VerifikasiIjazah.sol` menggabungkan registry, penyimpanan kredensial immutable, revocation, dan verifier attestation dalam satu batas ACL. `@fhevm/solidity 0.11.1` dikompilasi memakai solc 0.8.28. Plugin Hardhat 0.4.2, Hardhat 2.28.6, ethers 6.16.0, dan relayer-sdk 0.4.1 dikunci dalam lockfile. Kompilasi dan tes mock membuktikan penggunaan `euint256`, `add256`, serta `FHE.eq` tanpa pemotongan digest. Nama encoding `sha256-euint256-v1`.

Setiap digest SHA-256 memakai ABI encoding domain, credential ID, versi skema, field, dan nilai kanonis. File digest + salt membentuk upload commitment. Attestation EIP-712 juga mengikat request ID, versi normalizer/encoding/skema, konfigurasi OCR, hash handle, relayer, pembaca hasil, nonce, deadline, chain ID dan kontrak. Job nyata menggunakan ID acak 32 byte; URL sesi tetap wajib diotorisasi.

Penerbit mengenkripsi di browser dan menandatangani transaksi sendiri. Referensi hanya mendapat ACL kontrak dan wallet penerbit. Pembaca hasil mendapat ACL boolean per field dan agregat; relayer/admin tidak otomatis dapat mendekripsi referensi. Tidak ada public decryption. Admin registry memakai wallet dengan DEFAULT_ADMIN_ROLE; onboarding identitas institusi tetap tindakan administratif manusia.

Backend memakai lease persisten per relayer pada tabel PostgreSQL, dengan expiry dan owner token. Pemilik lama tidak dapat memperpanjang atau menghapus lease penggantinya; kepemilikan diperiksa kembali sebelum efek eksternal. Mekanisme ini kompatibel dengan Supabase transaction pooling dan tidak memakai session advisory lock. Transaksi ditandatangani, hash dan serialized transaction disimpan privat sebelum broadcast, lalu digunakan ulang saat retry. Request ID dan nonce ditolak bila dipakai ulang. Setelah dekripsi, status kredensial dan penerbit dibaca lagi pada blok yang memiliki minimum dua konfirmasi. Ini kebijakan konfirmasi prototipe, bukan jaminan finalitas Ethereum.

RPC ethers diberi timeout 20 detik dan operasi proof/dekripsi SDK 60 detik. Langkah Workflow yang dihasilkan SDK tetap mengikuti batas durasi paket Vercel; timeout dan retry tidak menggantikan pengujian jaringan Zama nyata.

## Retensi

Expiry akses artefak adalah satu jam setelah terminal atau maksimal 24 jam sejak intent/unggah; metadata riwayat minimal maksimal 24 jam. Penghapusan menulis tombstone sebelum menghapus storage. Penulisan hasil memeriksa tombstone dan generation token di transaksi yang sama, sehingga langkah Workflow yang terlambat tidak membuat ulang hasil privat. OCR tidak menulis dokumen ke disk; piksel dan teks hanya berada di memori selama langkah berjalan. Staging upload yang tidak difinalisasi kedaluwarsa dalam sepuluh menit; callback terlambat dan cleanup menghapus objek yatim tanpa membuat ulang job.

Pada Vercel, Workflow memproses unggahan segera dan menjadwalkan cleanup satu jam setelah pekerjaan terminal. Cron bawaan `0 0 * * *` menjalankan maintenance sekali sehari sesuai batas Hobby; Pro atau Enterprise dapat memakai jadwal lebih sering. Pemulihan dispatch yang gagal dan penghapusan fisik saat Workflow terhenti dapat menunggu maintenance berikutnya; pekerjaan bahkan dapat kedaluwarsa sebelum cron harian. API tetap menolak akses berdasarkan expiry, tetapi cron harian tidak menjamin penghapusan fisik tepat pada TTL ketika Workflow gagal. Cleanup diulang ketika layanan pulih. Tombstone intent tanpa filename/digest dipertahankan sebagai perlindungan callback terlambat. Vercel menolak fallback ke disk ephemeral.

Adapter Blob privat menjadi jalur hosting Vercel; token tidak pernah dikirim ke browser selain token upload terbatas. S3 privat dan storage disk tersedia untuk pengembangan/hosting alternatif. Pengujian Blob saat implementasi memakai mock termasuk upload 10 MiB, ownership, path tampering, signature, retry, penghapusan, expiry, dan callback palsu. Integrasi Blob/Supabase terkelola, deployment Vercel dengan OCR in-process, serta lifecycle object-store eksternal belum diuji dengan kredensial nyata. Tes migrasi/locking/lease dijalankan terhadap PostgreSQL lokal sekali pakai (`pnpm test:db`, service PostgreSQL di CI).

Laporan dibuat saat diunduh tanpa cache publik. PDF menyertakan digest file, commitment/salt, field OCR, versi konfigurasi, waktu/blok serta transaksi bila ada. Font Helvetica laporan mengubah karakter Unicode di luar cakupannya menjadi escape `\u{...}` secara eksplisit; tampilan web tetap Unicode penuh. Ini batas prototipe laporan yang perlu font Unicode tertanam sebelum penggunaan luas.

## Pengesahan dan jalur rekaman v1.2

`packages/credentials` menetapkan satu encoding ABI profil publik dan satu payload EIP-712. `contracts/src/VerifikasiIjazah.sol` hanya menerima penerbitan dengan signature payload, caller/signer yang sama, issuer terdaftar, commitment handle terurut, versi yang didukung, nonce, deadline, dan input proof yang valid. Bukti kewenangan signer saat penerbitan disimpan agar rotasi wallet tidak merusak rekaman historis. Hash nama institusi pada penerbitan mengikat snapshot lama meskipun metadata registry diperbarui.

Portal membekukan hasil enkripsi sebelum peninjauan dan signature. API draft menerima profil publik, domain, authorization, handle input, serta `documentDate` dari tanggal yang sama pada formulir penerbitan. Tanggal disimpan privat bersama snapshot draf, dibekukan terhadap perubahan, lalu disalin ke metadata bukti penerbitan; tidak masuk profil publik, payload EIP-712, QR, atau respons API publik. Ini merupakan pernyataan penerbit yang terautentikasi, bukan pembuktian tambahan bahwa tanggal plaintext sama dengan ciphertext. Input proof tetap tidak disimpan dalam draft. Signed proof disimpan sebelum broadcast, lalu diverifikasi dengan chain sebelum QR dapat dipublikasikan. Tabel Drizzle `credential_drafts` dan `signed_credentials` memakai RLS tanpa kebijakan akses anonim. Metadata privat tambahan memakai JSONB yang sudah ada, tanpa migrasi skema.

GET `/api/credentials/{id}/verification` memvalidasi domain dari konfigurasi server, signature, hash profil, credential digest, signer, commitment ciphertext, versi, serta bukti kewenangan historis. Pemeriksaan deadline/nonce hanya berlaku untuk pengajuan penerbitan baru. Endpoint publik tidak membuat sesi pekerjaan, menjalankan OCR, memuat kunci layanan, atau mendekripsi referensi. Profil hanya dikembalikan setelah bukti cocok; status pencabutan dan kewenangan saat ini ditampilkan terpisah dari validitas signature.

`completeExtraction` menggunakan hasil verifikasi rekaman sebelum enkripsi/transaksi perbandingan. Langkah Workflow memeriksa ulang signature serta status chain setelah hasil FHE tersedia. `INVALID_PROOF`, penerbitan pending, dan penerbit nonaktif tidak dapat menghasilkan `MATCH`. Laporan memisahkan tx penerbitan dan tx pencocokan, status rekaman dan keputusan dokumen, serta mencantumkan cakupan `CHECKED_ATTRIBUTES`.

Cleanup pekerjaan hanya menyentuh data sesi/pekerjaan/upload intent dan objek privat sementara. Ia tidak menghapus tabel bukti penerbitan. Payload yang hilang saat chain menemukan ID adalah gangguan bukti (`ERROR`), sedangkan kegagalan pembacaan chain tidak dipetakan menjadi `NOT_FOUND`.

## PDF penerbit tanpa ketergantungan OCR

`createDocument` memeriksa penandatangan aktif dan kepemilikan institusi, lalu memvalidasi bukti penerbitan. Profil PDF diambil dari bukti bertanda tangan. Tanggal penerbitan baru berasal dari snapshot privat; penggantian tanggal melalui permintaan PDF ditolak. Untuk kredensial lama tanpa snapshot tanggal, penerbit mengisi tanggal sesuai data penerbitan sebagai pernyataan penerbit; tanggal ini dibekukan saat pembuatan PDF pertama. Kecocokan terhadap referensi terenkripsi tetap merupakan fungsi verifikasi unggahan terpisah.

PDF langsung disimpan dengan hash konten ke arsip privat. Bukti/status pencabutan diperiksa lagi sebelum arsip berstatus `READY` dan setiap kali diunduh. Tidak dibuat job OCR, hasil `MATCH`, atau transaksi FHE. Retry kegagalan penyimpanan menggunakan timestamp, origin, tanggal, dan ID generasi yang sama. Arsip yang sudah siap tetap immutable. Dokumen lama yang tertahan OCR/antrean dapat dibuat ulang dengan generasi baru; callback job lama tidak dapat mengganti arsip baru. Berkas unggahan pengguna tetap harus melewati aturan verifikasi yang sama seperti sebelumnya.
